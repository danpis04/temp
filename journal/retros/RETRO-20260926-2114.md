## Backfill: how the gap happened

`core/counterfactual.py reconcile` flagged 3 unentered `outside-view-veto`
rows; diffing `journal/forecasts.jsonl` against `cycles.log`/retros found
2 more `wide-spread-veto` rows and 2 plain `no-edge` rows from the same
chain, all silently settled:

- **19:16Z LIGHT tick (commit `769bd23`)**: `resolve.py` settled 4 MrBeast
  forecasts (2 `outside-view-veto`, 2 `market-agrees`) but the cycle log
  line reads "0 forecasts settled" — a factual error in that entry — and
  no retro was written, violating the schedule.json LIGHT-tick rule
  ("settles ANYTHING" includes forecasts).
- **20:25Z FULL cycle (commit `1458112`)**: `resolve.py` settled these 4
  plus 4 more of the same chain (2 `wide-spread-veto`, 2 `no-edge`) in the
  same run that also settled 4 UNL forecasts, but `RETRO-20260926-2007`
  and the cycle log only mention the UNL rows — the MrBeast half of
  `resolve.py`'s own printed output was dropped.
- **Older**: `56ed434261a5` (Yabloko, Russian Duma) was graded narratively
  in `RETRO-20260925-1105` but that retro explicitly said "no stake, so no
  counterfactual veto table entry is owed" — incorrect; forecast-only
  `outside-view-veto` rows are exactly what the table exists to track (every
  other row in it is unstaked). That's a one-off misreading, not a repeat
  pattern.

Lesson for future cycles: read `resolve.py`'s full stdout line-by-line
before drafting the retro — it prints every settled row in one pass, and
grading a subset because the retro was drafted around one obvious cluster
(UNL matches, Duma results) is how rows get dropped even though the data
was sitting right there.
